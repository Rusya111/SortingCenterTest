## Блок 1. Создание заказа

### TC-01. Создание заказа с валидными данными
**Предусловие:** открыта главная страница, выбран город "Уфа".
**Шаги:**
1. Нажать "Новый заказ".
2. Заполнить номер заказа: `UF-9999`.
3. Заполнить грузоместо: `CN-99999`.
4. Выбрать отгрузку: `Уфа`, поставку: `Самара`.
5. Статус: `В процессе`. Проблема: `Дубль`.
6. Нажать "Создать".
**Ожидаемый результат:** Редирект на главную. В таблице появился заказ `UF-9999`. В БД (проверял через DBeaver) появилась запись с датой в UTC. Заказ принадлежит городу "Уфа".
**Фактический результат:** Все работает как задумано. Заказ появился в таблице, в БД запись есть, дата сохранилась в UTC. Кейс пройден.

### TC-02. Попытка создать заказ с пустыми полями
**Шаги:**
1. Открыть форму создания.
2. Ничего не вводить (или заполнить только одно поле).
3. Нажать "Создать".
**Ожидаемый результат:** Форма не отправляется на сервер (блокируется валидацией на клиенте). Под обязательными полями вылезают красные сообщения. Запись в БД не создается.
**Фактический результат:** Валидация сработала корректно. Форма не ушла на сервер, подсветились красным пустые поля. Запись в БД не создалась. Кейс пройден.

### TC-03. Ввод слишком длинного номера заказа
**Шаги:**
1. Открыть форму создания.
2. Ввести в номер заказа строку из 100 символов (например, `AAAAAAAA...`).
3. Заполнить остальные поля и нажать "Создать".
**Ожидаемый результат:** Либо форма не дает отправить (если есть ограничение по длине `MaxLength`), либо заказ создается, и таблица не разъезжается при отображении длинного текста.
**Фактический результат:** Ограничения на длину в модели нет, поэтому заказ создался. В таблице длинный текст переносится на новую строку, верстка не ломается. Кейс пройден (но с замечанием, что `MaxLength` стоит добавить).

## Блок 2. Поиск

### TC-04. Поиск по точному номеру заказа
**Предусловие:** в системе есть заказ `UF-1001` и `GR-2001`.
**Шаги:**
1. В поле поиска ввести `UF-1001`.
2. Нажать "Поиск".
**Ожидаемый результат:** В таблице остался только `UF-1001`. Остальные скрылись.
**Фактический результат:** Точный поиск работает корректно. Отображается только нужный заказ. Кейс пройден.

### TC-05. Поиск по частичному совпадению
**Предусловие:** (Этот кейс упал из-за BUG-01, потом починил).
**Шаги:**
1. Ввести в поиск `CN-123`.
2. Нажать "Поиск".
**Ожидаемый результат:** Отображаются все заказы, где в грузоместе есть `CN-123` (например, `CN-12345`, `CN-12346`).
**Фактический результат:** Первый прогон упал — поиск ничего не находил (BUG-01). После исправления на `.Contains()` кейс проходит: отображаются все заказы с подстрокой `CN-123`. Кейс пройден после фикса.

### TC-06. Поиск по несуществующему номеру
**Шаги:**
1. Ввести `FAKE-0000`.
2. Нажать "Поиск".
**Ожидаемый результат:** Таблица пустая. Выводится сообщение, что ничего не найдено (заглушка "Заказы не найдены"). Сайт не падает.
**Фактический результат:** Таблица пустая, появляется предупреждение "Заказы не найдены. Проблемы: ...". 500-й ошибки нет. Кейс пройден.

### TC-07. Поиск при переключенном городе
**Предусловие:** выбран город "Грибки" (там есть заказ `GR-2001`).
**Шаги:**
1. Ввести в поиск `GR-2001`.
2. Нажать "Поиск".
**Ожидаемый результат:** Заказ найден. Город не сбрасывается на "Уфа" (в URL и в заголовке остается "Грибки").
**Фактический результат:** Заказ найден, в заголовке и URL остается "Грибки" (параметр `currentUser` передается через hidden input в форме поиска). Кейс пройден.

### TC-08. Успешное редактирование заказа
**Предусловие:** (Сначала падало из-за BUG-02, но потом починил).
**Шаги:**
1. На главной странице нажать "Редактировать" у заказа `UF-9999`.
2. Изменить номер грузоместа с `CN-99999` на `CN-00000`.
3. Нажать "Сохранить".
**Ожидаемый результат:** Редирект на главную. В таблице у заказа `UF-9999` указан новый грузомест `CN-00000`. В БД (DBeaver) значение обновилось.
**Фактический результат:** Первый прогон упал — редирект был, но данные не менялись (BUG-02). После переписывания метода `Edit` (обновление через `existingOrder`) кейс проходит: изменения видны и в таблице, и в БД. Кейс пройден после фикса.

### TC-09. Попытка сохранить редактирование с пустым обязательным полем
**Шаги:**

**Фактический результат:** Валидация сработала, форма не отправилась, на странице появились сообщения об ошибке. Данные в БД не изменились. Кейс пройден.

## Блок 4. Скрытие и восстановление (тут был BUG-04)

### TC-10. Скрытие заказа
**Шаги:**
1. На главной найти любой заказ.
2. Нажать на желтую кнопку с "глазиком" (скрыть).
**Ожидаемый результат:** Заказ исчезает из основной таблицы. Сверху вылезает зеленое уведомление "Заказ скрыт". В DBeaver у этого заказа флаг `IsHidden = true`.
**Фактический результат:** Заказ исчез, уведомление появилось, флаг в БД переключился в `true`. Кейс пройден.

### TC-11. Восстановление заказа
**Предусловие:** есть скрытый заказ (из TC-10). Сначала тут был баг, заказ не возвращался.
**Шаги:**
1. Нажать "Скрытые заказы".
2. Найти нужный заказ.
3. Нажать на кнопку "показать" (зеленый глазик).
**Ожидаемый результат:** Заказ возвращается в основной список на главной. В DBeaver флаг `IsHidden = false`.
**Фактический результат:** Первый прогон упал — заказ пропадал со страницы скрытых, но на главную не возвращался (BUG-04). После исправления логики переключения `IsHidden` кейс проходит. Кейс пройден после фикса.

## Блок 5. Разделение по городам (тут был BUG-03)

### TC-12. Отображение только своих заказов
**Предусловие:** в БД есть заказы и для "Уфы", и для "Грибков".
**Шаги:**
1. Выбрать в шапке город "Уфа".
2. Посмотреть таблицу.
3. Переключиться на "Грибки".
4. Посмотреть таблицу.
**Ожидаемый результат:** В Уфе видны только заказы с `UserSC = "Уфа"`. В Грибках - только с `UserSC = "Грибки"`. (Сначала тут была свалка из всех заказов).
**Фактический результат:** Первый прогон упал — везде отображались все заказы (BUG-03). После добавления фильтра `.Where(o => o.UserSC == currentUser)` кейс проходит: каждый город видит только свои заказы. Кейс пройден после фикса.

## Блок 6. Удаление

### TC-13. Удаление заказа с подтверждением
**Шаги:**
1. Нажать на красную кнопку "корзина" у любого заказа.
2. В появившемся окне подтверждения нажать "ОК".
**Ожидаемый результат:** Заказ удален из таблицы. Редирект на главную с сообщением "Заказ успешно удален". В БД записи нет.
**Фактический результат:** Окно подтверждения появляется, но после нажатия "ОК" вылетает ошибка 400 Bad Request (BUG-05). Заказ не удаляется. Кейс упал, баг заведен.

**Фактический результат:** При нажатии "Отмена" ничего не происходит, заказ остается на месте. Кейс пройден.

**Фактический результат:** *(Проверял на разрешении 1366x768. Если текст длинный, таблица начинает скроллиться горизонтально. Это не баг, но UX-момент — можно поправить стилями).*

### TC-20. Проверка, что скрытый заказ не отображается при поиске
**Предусловие:** заказ `UF-9999` скрыт.
**Шаги:**
1. Находясь на главной, ввести в поиск `UF-9999`.
2. Нажать "Поиск".
**Ожидаемый результат:** Заказ не найден (потому что он скрыт и лежит в другой вкладке). Поиск не должен "вытаскивать" скрытые заказы в основной список.

**Фактический результат:** В контроллере стоит фильтр `!o.IsHidden` до применения поиска, поэтому скрытые не должны попадать. Но надо перепроверить, что запрос действительно не срабатывает на скрытых.
